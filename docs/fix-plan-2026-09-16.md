## P1-1 — `allowed_tools` validation is case-sensitive, and total rejection hard-errors

**Symptom.** The agent delegated successfully twice, then failed six times in two
rounds and finally burned a 180-second timeout:

```
18:48:49,968  delegate_to_agent        -> exit_code=0
18:48:49,972  delegate_to_claude_code  -> exit_code=0
18:49:02,944  delegate_to_agent -> exit_code=1  unsafe allowed tool(s) ['read','grep','glob','bash']
18:49:02,947  delegate_to_agent -> exit_code=1  (byte-identical)
18:49:02,949  delegate_to_agent -> exit_code=1  (byte-identical)
18:49:12,62x  round 3: 3 more native calls
18:52:13,039  delegate_to_agent -> exit_code=124  Claude Code timed out after 180s
```

**Root cause.** `SAFE_TOOL` (`src/agent_tools/claude_code_tools.py:99`) is compiled
without `re.IGNORECASE`:

```python
SAFE_TOOL = re.compile(rf"^(Read|Glob|Grep|Edit|Write|Bash\(git …")
```

The model sent lowercase, so every entry was rejected, `len(rejected) == len(tools)`
was true, and control took the hard-error branch at line 424 instead of the
mixed-list branch immediately below it. That branch's own comment states the
principle the hard-error branch violates:

> A mixed list runs with its safe entries. Refusing the whole job cost the
> 2026-09-13 run three rounds re-sending one list with `git push` and a malformed
> entry in it; dropping can only narrow Claude's rights.

If dropping can only narrow rights, dropping *all* of them and falling back to
`default_tools()` is strictly safer than refusing the job. The all-rejected case is
the one place that reasoning was not applied.

**Fix.**
1. Canonicalise case before matching — map `read`/`READ` to `Read` and so on — so a
   lowercase list is accepted rather than silently reinterpreted.
2. Make the all-rejected branch behave like the mixed branch: fall back to
   `default_tools()` and return `dropped_tools` / `dropped_note` rather than an error.

**Tests.**
- `allowed_tools=['read','grep']` runs with `['Read','Grep']`.
- `allowed_tools=['rm -rf /']` runs with the defaults and reports `dropped_note`.
- A mixed list keeps its existing behaviour (regression guard for 2026-09-13).

## P1-2 — The failure names a tool the model did not call

**Symptom.** A `delegate_to_agent` call is told to fix `delegate_to_claude_code`:

```
Tool executed: delegate_to_agent -> exit_code=1 error=delegate_to_claude_code: unsafe allowed tool(s) …
```

**Root cause.** `src/tool_execution.py:1356` dispatches both names through one
branch, and every error string in `claude_code_tools.py` hardcodes
`delegate_to_claude_code:`.

**Fix.** Thread the invoked tool name through to the error prefix. A model that
cannot tell which of two tools it broke cannot correct itself — this is what turned
one bad argument into six rounds.

**Test.** A failing `delegate_to_agent` call returns a message beginning
`delegate_to_agent:`.

## P1-3 — The duplicate-call guard ignores failures

**Symptom.** Three byte-identical failing calls in round 2, three more in round 3.
The guard exists precisely to stop this and did not fire.

**Root cause.** The dedupe memo records successful calls. A repeat that failed
identically is the case where repeating is most certainly useless, and it is the
case that is not covered.

**Fix.** Record failing calls in the memo too. After two identical failures, emit a
directive quoting the error instead of executing a third time — reuse the existing
`_MAX_DUP_CALL_DIRECTIVES` machinery rather than adding a new counter.

**Test.** The same failing signature three times: the third is suppressed and a
directive naming the error is injected.

## P1-4 — Agent-management tools escape the delegation gate

**Symptom.** On `run the agent tests` the gate correctly refused the delegation
tools — and then the model started a remote worker anyway:

```
18:47:46  dropped_query_matches=[('delegate_to_agent','delegation-policy:explicit'),
                                 ('delegate_to_claude_code','delegation-policy:explicit'),
                                 ('message_agent','delegation-policy:explicit')]
18:47:46  selected_tools=… manage_agent_loadout, manage_agent_worktree, mcp__pi_worker__run_pi_task …
18:47:51  Tool executed: mcp: mcp__pi_worker__run_pi_task -> exit_code=0
```

**Root cause.** `_DELEGATION_TOOLS` (`src/agent_loop.py:1619`) enumerates six names:
`delegate_to_agent`, `delegate_to_claude_code`, `send_to_session`, `message_agent`,
`pipeline`, `create_session`. `manage_agent_loadout` — which creates *and starts*
agent loadouts — is not among them. Neither is the pi_worker MCP tool.

**Fix.**
1. Add `manage_agent_loadout` to `_DELEGATION_TOOLS`. Starting a loadout is starting
   an agent; the gate should not distinguish by which tool does it.
2. Decide deliberately on the other two and write the decision down:
   - `manage_agent_worktree` manages a checkout, not an agent — probably stays out.
   - `mcp__pi_worker__run_pi_task` is remote execution and probably belongs in a
     gate, though not necessarily this one.

The general principle: the gate is a list of names, so every new tool that can start
work elsewhere has to be added by hand. Consider deriving membership from a
capability flag on the tool definition instead, so the next one cannot be forgotten.

**Test.** `run the agent tests` selects none of the agent-starting tools.

## P2-5 — `web_search` queries every provider twice

**Symptom.** The identical SearXNG request, its identical drift-retry, and the
identical DuckDuckGo fallback each fire twice per search:

```
18:46:10,365  searxng  site:… → 5 off-domain dropped → retry with 'github.com'
18:46:10,610  searxng  retry                        → 5
18:46:10,898  searxng  SAME site: query again       → 5 off-domain dropped
18:46:11,127  searxng  same retry again             → 5
18:46:52,297  duckduckgo html → 0
18:46:52,446  duckduckgo html, same query → 0
```

The same doubling appears at 18:46:51. Every web search costs twice the upstream
round-trips and twice the rate-limit budget.

**Root cause.** Not yet located. The `site:`-drift detection itself is correct — it
is the comprehensive-search path being entered twice per call. Start at
`services/search/core.py`, `Starting comprehensive search for:` (logged once, so the
duplication is below that line, likely a provider list containing the same provider
twice or a retry wrapper around an already-retrying call).

**Test.** One `web_search` invocation issues one request per provider per distinct query.

## P2-6 — No relevance gate outside the `site:` path

**Symptom.** A search for this repository returned Japanese travel pages, and the
harness fetched four of them in full and fed them to the model:

```
18:46:56  query: "robertsima/odysseus-main" "poller"  → searxng 5 results
18:46:56  GET getyourguide.com/pt-br/explorer/sapporo-…
18:46:57  GET gotripzi.com/…/sapporo-jp
18:46:59  GET quantocustaviajar.com/japao/sapporo
18:46:59  GET skyscanner.com.br/…/sapporo
18:46:59  Successfully fetched content from 4 pages
18:46:59  [tool-output] offloaded 10116 + 10120 + 10115 + 1083 chars from web_fetch
```

~31k characters of travel content entered the run as research on an email poller.

**Root cause.** The `site:` path has a drift check that correctly drops off-domain
results. The plain-query path has none: whatever the provider returns is fetched.

**Fix.** Apply the same check to every query. If no result shares a significant token
with the query, return empty and the existing "rephrase or use the browser tool"
guidance rather than fetching. That guidance string already exists — it is emitted at
18:46:52 for the `site:` case.

**Test.** A query with zero token overlap against its results yields 0 results and
issues no fetches.

## P2-7 — The agent declines a capability it has

**Symptom.**

```
18:55:27  "I can't determine your next meeting because calendar access isn't
           available in this session."
```

`manage_calendar` exists and was selected 8 minutes earlier at 18:47:15. It was
absent here only because the turn's retrieval query was about ntfy
(`domains=[]` at 18:55:18), so no calendar tool was bound.

**Root cause.** The missing-tool recovery path did not fire. The model stated the
capability was unavailable rather than re-arming the toolset — the same failure class
as the earlier `_SKILL_TOOLSET_ALIASES` bug, in a different trigger.

**Fix.** Treat a self-reported "X is not available in this session" as a re-arm
signal, not a final answer. Check why the existing self-unblock did not engage —
it may key on tool-call failure rather than on prose.

**Test.** A turn needing an unselected tool re-arms and completes instead of declining.

## P2-8 — Tool retrieval has no similarity floor

**Symptom.** `use ntfy to send a notification to odysseus` retrieved 21 tools,
including the entire email suite:

```
18:55:18  Retrieved tools for query: ['app_api','archive_email','audit_emails',
          'bulk_email','delete_email','list_email_accounts','list_emails',
          'manage_agent_worktree','mark_email_read','mcp__51452cf0__ntfy_me', …]
18:55:18  query_matched_count=21 selected_count=27   schema_tokens=4787
```

**Root cause.** Already documented in the code, at `src/agent_loop.py:5566`: *"the
index has no similarity cutoff, so a chat turn like 'i like Umni' was still handed
its eight nearest tools."* The low-signal path works around this by skipping
retrieval entirely; a request-shaped query still gets its nearest neighbours whatever
the distance.

**Fix.** Add a similarity floor to tool retrieval so a far neighbour is dropped
rather than bound. This removes the need for the low-signal special case to exist as
a separate mechanism.

**Test.** The ntfy query binds the ntfy tools and the always-available set, not the
email suite.

## P3-9 — The cached prefix breaks mid-turn

**Symptom.**

```
18:45:55  round=1  input=26911  cached=3584
18:46:00  round=2  input=28424  cached=0      ← prefix broken
18:46:05  round=3  input=30182  cached=28160  ← recovered
```

`tools_sent=33` and `schema_tokens=4500` are identical across all three rounds, so
the toolset is not the cause. One round paid ~28k uncached tokens.

**Fix.** Instrument first: log a hash of the cached prefix per round, then find what
mutates it between rounds 1 and 2. This is the failure
`specs/prompt-prefix-stability.md` exists to prevent, so the spec likely needs a
test, not just prose.

## P3-10 — `[tool-rag]` logs two contradictory lines

**Symptom.** 25 milliseconds apart, on the same turn:

```
18:44:33,803  [tool-rag] Low-signal query; keyword hints only (no embedding retrieval)
18:44:33,828  [tool-rag] Retrieved tools for query: []
```

**Fix.** Suppress the `Retrieved tools` line on the hints-only path.

**Why it matters beyond tidiness.** This log pair is what produced an earlier wrong
conclusion that embedding retrieval was being skipped on most messages. It was not —
every request-shaped turn retrieved correctly. A log line that misreports which
branch ran costs more than a missing one.

## Not a bug: the 180-second delegation timeout

`claude_code_tools.py:412` clamps `timeout_seconds` to 30–1800 with a default of 900.
The 180 at 18:52:13 was the model's own choice, not a cap. The schema should steer a
repository-wide audit toward `action="start"` plus polling rather than `action="run"`
with a short timeout — a description change, not a code fix.
